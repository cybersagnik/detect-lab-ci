# T1047 — Windows Management Instrumentation (WMI) Process Execution

## Hypothesis
Adversaries abusing WMI's `Win32_Process.Create()` method (invoked through `wmic.exe`) to spawn processes locally or remotely, providing execution without dropping a binary on disk. WMI execution is one of the canonical living-off-the-land patterns because `wmic.exe` is a signed Microsoft binary trusted by application whitelisting and leaves minimal forensic artefacts beyond the WMI event log.

## Threat actor context
Used by: APT32, APT41, Lazarus Group, FIN7, Cobalt Strike default beacon, and most post-exploitation frameworks. WMI execution is the default lateral-movement mechanism in Cobalt Strike and Empire, and is present in the vast majority of enterprise ransomware playbooks for execution and persistence.

## Telemetry required
- **Sysmon EventID 1** (ProcessCreate)
- `Image` ending with `\wmic.exe`
- `CommandLine` containing `process call create` (the `Win32_Process.Create()`
  invocation) or `process` + `call` + `create` separately
- The child process spawned as a result — its `Image` and `CommandLine`
  are the actual payload

## Why standard detection misses this
Endpoint protection typically allows `wmic.exe` because it is a legitimate
administrative tool. WMI read-only queries (`Win32_OperatingSystem`,
`Win32_ComputerSystem`) are extremely common in monitoring agents and
infrastructure scripts, so simple WMI alerting generates high-volume noise.
The signal must distinguish read-only WMI queries from process-creation
WMI calls, which basic loggers cannot do without Sysmon EID 1 visibility
into the `wmic.exe` CommandLine.

## Detection logic
```yaml
detection:
  selection:
    Image|endswith: '\wmic.exe'
    CommandLine|contains:
      - 'process'
      - 'call'
      - 'create'
  filter_legitimate:
    CommandLine|contains:
      - 'Win32_Processor'
      - 'Win32_ComputerSystem'
      - 'Win32_OperatingSystem'
  condition: selection and not filter_legitimate
```

## Lab validation
- ART Test: `Invoke-AtomicTest T1047 -TestNumbers 5`
- ART Test Name: WMI Execute Local Process
- Alert fired: Yes — Sysmon EID 1
- CommandLine confirmed: `wmic process call create notepad.exe`
- Image confirmed: `C:\Windows\System32\wbem\WMIC.exe`
- `notepad.exe` spawned as the child process (ProcessId visible in WMI output)

## Filter rationale
The `filter_legitimate` block excludes `wmic.exe` invocations that query
read-only WMI classes commonly used by monitoring tools and inventory
agents. `Win32_Processor`, `Win32_ComputerSystem`, and `Win32_OperatingSystem`
are the three classes most frequently accessed by legitimate management
software — they do not result in process creation and have no security
relevance. Filtering on these strings removes the high-volume background
of monitoring activity while preserving the smaller but higher-fidelity
set of `wmic process call create` invocations that indicate execution.

## Analyst triage guidance
On alert, check the `CommandLine` argument after `create` and the child
process `Image` in Wazuh:
- The literal string passed to `create` is the payload — copy it from the
  CommandLine. If it is a full path under `C:\Windows\System32\`
  (`notepad.exe`, `calc.exe`) it is likely the ART test pattern; investigate
  the originating process
- If the child `Image` is `powershell.exe`, `cmd.exe`, `rundll32.exe`,
  `mshta.exe`, or `regsvr32.exe` — escalate immediately, this is the
  canonical WMI execution chain
- A `wmic process call create "C:\ProgramData\...\payload.exe"` is
  high-confidence malicious — the writeable location plus WMI execution
  is a textbook post-exploitation pattern
- `wmic ... /node:"<remote-host>"` indicates lateral execution via WMI —
  review the remote target and the source machine's session logon events
