# T1140 — Deobfuscate / Decode Files or Information via certutil.exe

## Hypothesis
Adversaries abusing `certutil.exe` to decode Base64-encoded payloads or to fetch remote files via its `-urlcache` flag. Because `certutil.exe` is a signed Microsoft binary trusted by application whitelisting and is normally used only for certificate management, its invocation with `-decode`, `-urlcache`, `-split`, or `-f http` flags is a high-fidelity indicator of payload staging or living-off-the-land file download.

## Threat actor context
Used by: APT32, APT34, Cobalt Strike default beacon, PowerSploit, and most commodity loaders. The `certutil -decode` pattern is the most common Base64-decoding primitive observed across public offensive frameworks because it requires no additional binary on disk and bypasses most application-whitelisting solutions.

## Telemetry required
- **Sysmon EventID 1** (ProcessCreate)
- `Image` ending with `\certutil.exe`
- `CommandLine` containing one or more decode / fetch flags:
  `-decode`, `-urlcache`, `-split`, `-f http`
- The output file path (decoded to) — `C:\Users\...`, `C:\ProgramData\...`,
  `C:\Windows\Temp\...` are the common staging locations

## Why standard detection misses this
`certutil.exe` is a trusted Microsoft binary that endpoint protection
typically allows. Its `-decode` and `-urlcache` flags are not invoked by
any first-party software — certificate management workflows never use
these flags. The detection signal is the flag combination rather than
the binary itself, and basic command-line logging without flag awareness
treats any `certutil.exe` invocation as legitimate certificate management.

## Detection logic
```yaml
detection:
  selection:
    Image|endswith: '\certutil.exe'
    CommandLine|contains:
      - '-decode'
      - '-urlcache'
      - '-split'
      - '-f http'
  condition: selection
```

## Lab validation
- ART Test: `Invoke-AtomicTest T1140 -TestNumbers 1`
- ART Test Name: Deobfuscate / Decode Files Or Information
- Alert fired: Yes — Sysmon EID 1
- **Wazuh Hit Count: 2** — both the encode step and the decode step
  fired (ART runs encode then decode in sequence)
- CommandLine observed:
  `certutil -encode C:\Windows\System32\calc.exe C:\Users\raysa\AppData\Local\Temp\T1140_calc.txt`
- The encode step writes Base64 to a Temp path; the decode step writes
  the resulting binary back to a user-writable location
- Both operations are visible in the Wazuh dashboard with the same
  certutil image and different flags

## Filter rationale
No filter applied — `certutil.exe` legitimately handles certificates
but the `-decode`, `-urlcache`, `-split`, and `-f http` flags are not
used in normal certificate management workflows. The flag combination
is specific enough that additional filtering would only reduce coverage
of a technique with very high adversary prevalence.

## Analyst triage guidance
On alert, check `CommandLine` and the output file path in Wazuh:
- Identify the output path from the argument after `-decode` — if it
  resolves to `C:\Users\`, `C:\ProgramData\`, `C:\Windows\Temp\`, or
  any user-writable directory — escalate
- If the command decodes a file in-place from a URL
  (`-urlcache -split -f http://...`) — high-confidence remote payload
  staging, isolate the host
- Cross-reference with EID 11 (FileCreate) immediately after the alert
  to identify the file written to disk — quarantine if it is not a
  known certificate artefact
- A `certutil -decode` against an output file under `C:\Windows\System32\`
  masquerading as a legitimate binary is a sophisticated variant —
  review the hash of the decoded file against the expected vendor hash
