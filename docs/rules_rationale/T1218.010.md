# T1218.010 — Regsvr32 Proxy Execution (Squiblydoo)

## Hypothesis
Adversaries abusing `regsvr32.exe` to proxy execution of malicious COM scriptlets (`.sct`) via the `/i:` flag combined with `scrobj.dll`. The technique — known publicly as "Squiblydoo" — leverages `regsvr32.exe`'s legitimate COM registration workflow to load an attacker-controlled scriptlet that VBScript or JScript executes in-process, bypassing application whitelisting without writing a `.vbs` or `.js` file to disk.

## Threat actor context
Used by: APT19, APT32, Cobalt Strike default beacon, PowerSploit, and most commodity phishing kits. Squiblydoo was the first widely-publicised `regsvr32.exe` abuse pattern and remains in active use more than a decade after disclosure because it requires no on-disk payload, evades most application-whitelisting solutions, and is invoked via a signed Microsoft binary.

## Telemetry required
- **Sysmon EventID 1** (ProcessCreate)
- `Image` ending with `\regsvr32.exe`
- `CommandLine` containing the proxy-execution flag pattern:
  `/i:` (the COM scriptlet reference) and either `http` (remote URL)
  or `scrobj` (the COM moniker for scriptlet loading)

## Why standard detection misses this
`regsvr32.exe` is a legitimate first-party Microsoft binary invoked
constantly by Windows Update, Office, and enterprise application
installers to register COM components. Endpoint protection typically
allows its execution. The distinguishing signal is the combination of
the `/i:` flag with a remote URL or a `.sct` scriptlet — basic loggers
that only record the binary name cannot distinguish benign COM
registration from scriptlet proxy execution.

## Detection logic
```yaml
detection:
  selection:
    Image|endswith: '\regsvr32.exe'
    CommandLine|contains:
      - 'http'
      - 'scrobj'
      - '/i:'
      - '-i:'
  filter_legitimate:
    CommandLine|endswith:
      - '.dll'
      - '.ocx'
  condition: selection and not filter_legitimate
```

## Lab validation
- ART Test: `Invoke-AtomicTest T1218.010 -TestNumbers 1`
- Alert fired: Yes — Sysmon EID 1
- **Wazuh Hit Count: 4** — multiple regsvr32 invocations during the test
- CommandLine observed:
  `C:\Windows\system32\regsvr32.exe /s /u /i:"C:\AtomicRedTeam\atomics\T1218.010\src\RegSvr32.sct" scrobj.dll`
- The `/i:` argument points at a local `.sct` COM scriptlet and the
  `scrobj.dll` moniker — the canonical Squiblydoo bypass pattern
- ART runs regsvr32 multiple times during the test (scriptlet load,
  retry, cleanup), producing multiple Sysmon EID 1 events

## Filter rationale
The `filter_legitimate` block excludes `regsvr32.exe` invocations whose
CommandLine ends with `.dll` or `.ocx`. Standard regsvr32 usage is to
register COM components by path only — `regsvr32.exe somelibrary.dll`
or `regsvr32.exe somecomponent.ocx`. These invocations do not use the
`/i:` flag and do not reference `scrobj.dll`. The filter retains the
Squiblydoo pattern (where the scriptlet is loaded via `scrobj.dll` and
the argument is a `.sct` or a URL) while suppressing the high-volume
background of normal COM registration activity.

## Analyst triage guidance
On alert, check `CommandLine` and the `/i:` argument in Wazuh:
- If `/i:` resolves to an `http://` or `https://` URL — confirmed
  remote Squiblydoo, isolate the host immediately
- If `/i:` resolves to a local `.sct` file, examine the file's path:
  - Paths under `C:\AtomicRedTeam\`, `C:\Windows\Temp\`,
    `C:\ProgramData\`, or `C:\Users\Public\` are malicious — escalate
  - Paths under a known vendor installation directory may be a
    legitimate COM component registration — review the file signature
- The `scrobj.dll` moniker in the CommandLine is the canonical
  Squiblydoo indicator — its presence alongside `/i:` should be
  treated as high-confidence malicious regardless of the scriptlet path
- Cross-reference with EID 7 (ImageLoad) for `scrobj.dll` loading from
  the parent regsvr32 process — confirms the scriptlet execution chain
