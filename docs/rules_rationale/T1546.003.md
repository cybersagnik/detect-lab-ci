# T1546.003 — WMI Event Subscription Persistence

## Hypothesis
Adversaries creating WMI event subscriptions (a Filter + Consumer + Binding triplet) to establish persistence that survives reboots and is invisible to most endpoint protection. The filter defines the trigger condition (timer, log event, process creation), the consumer defines what runs (command line, script, executable), and the binding wires them together. Once registered, the WMI service executes the consumer automatically whenever the filter matches — making this one of the stealthiest persistence mechanisms in the Windows toolkit.

## Threat actor context
Used by: APT29, APT32, Lazarus Group, FIN7, Cobalt Strike default beacon, and most nation-state actors performing long-term dwell operations. WMI event subscription persistence is the preferred mechanism for "low and slow" intrusions because the WMI repository persists in `C:\Windows\System32\wbem\Repository\` and is rarely inspected during incident response.

## Telemetry required
- **Sysmon EventID 19** — WmiEventFilter (the trigger condition created)
- **Sysmon EventID 20** — WmiEventConsumer (the action to execute, created)
- **Sysmon EventID 21** — WmiFilterToConsumerBinding (links filter to consumer)
- Any of EID 19, 20, or 21 firing indicates WMI subscription activity —
  both initial creation and later modification
- `Destination` field on EID 20 — the command line / script / executable
  that will run when the filter triggers
- `Name` field on EID 19/20 — the named subscription object
- `Query` field on EID 19 — the trigger condition

## Why standard detection misses this
WMI event subscriptions live in the WMI repository, not in the
registry's standard Run keys or in the Task Scheduler — so signature-
based autorun detection misses them entirely. Default Sysmon
configuration does not enable EID 19/20/21 logging, and even when
enabled, the events are low-volume enough that most SOC tooling
suppresses them by default. The technique is invisible to file-system-
based persistence scanning.

## Detection logic
```yaml
detection:
  selection:
    EventID:
      - 19
      - 20
      - 21
  condition: selection
```

## Filter rationale
No filter applied — legitimate software rarely uses WMI event
subscriptions. The only common legitimate users are enterprise
management platforms (SCCM, some AV products) and a small number of
monitoring agents. The signal-to-noise ratio is high enough that
filtering would only suppress valid detections. A environment-specific
list of legitimate subscription names can be added to the filter block
in deployments where SCCM or a known monitoring agent is present, but
the default rule detects all subscription activity.

## Analyst triage guidance
On alert, check the Wazuh message field and correlate EID 19, 20, 21:
- EID 20 `Destination` field shows WHAT will execute — if it resolves
  to `powershell.exe`, `cmd.exe`, `rundll32.exe`, `mshta.exe`, or any
  script interpreter — escalate immediately
- EID 20 `Type` field shows HOW it will execute:
  - `Command Line` (a command will run) — most common malicious pattern
  - `ActiveScript` (a VBScript / JScript will execute) — high severity
- EID 19 `Query` field shows WHEN it triggers — `SELECT * FROM __InstanceCreationEvent WITHIN 60 WHERE TargetInstance ISA 'Win32_Process'`
  is a process-creation trigger; timer-based triggers are equally
  suspicious
- EID 21 `Consumer` + `Filter` fields confirm the binding — both must
  reference legitimate `__EventFilter` and `__EventConsumer` objects in
  the `ROOT\subscription` namespace
- A subscription created by a non-administrator process (check EID 1
  around the timestamp of EID 20) is high-confidence malicious —
  legitimate WMI subscriptions are created by SYSTEM or enterprise
  management agents
